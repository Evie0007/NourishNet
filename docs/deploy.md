# Deploying NourishNet

Two pieces, two hosts:

| Piece | Host | Why |
|---|---|---|
| `frontend/` | Vercel | Static build, already there |
| `backend/` (API) | Render | Needs a long-lived process — for the expiration sweep, and so SQLAlchemy's connection pool isn't rebuilt per request |
| Database | Supabase | Already running |

Both hosts build from the same repo and each ignores the other's half:
`render.yaml` sets `rootDir: backend`, and `.vercelignore` hides `backend/`
so Vercel doesn't mistake the Python for a serverless function.

---

## 1. Push the repo

Render deploys from GitHub, so the code has to be pushed before anything else.
Confirm no secrets are going with it:

```bash
git status              # .env must NOT appear
git check-ignore -v .env gcp-vision-key.json nourishnet.db nourishnet_local.db
```

All four should be reported as ignored. `.env.example` is the committed
template and contains no real values.

## 2. Create the Render service

1. Render dashboard → **New** → **Blueprint**
2. Connect `github.com/Evie0007/NourishNet`
3. Render reads [`render.yaml`](../render.yaml) and proposes a service named
   `nourishnet-api`. It will prompt for the two values the file deliberately
   doesn't contain:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Your Supabase connection string, exactly as in local `.env` |
| `CORS_ORIGINS` | Your Vercel URL, e.g. `https://nourishnet.vercel.app` |

`JWT_SECRET` is generated by Render — don't paste the local one.

**The `DATABASE_URL` host must be the pooler** (`…pooler.supabase.com`), not
the direct `db.…supabase.co` host. Supabase's direct connections are
IPv6-only and Render can't reach them. The URL already in your `.env` is the
pooler one, so copy it as-is.

**`CORS_ORIGINS` must be an exact origin match** — `https://`, no trailing
slash, no path. `https://nourishnet.vercel.app/` (trailing slash) will not
match and every request from the browser will fail.

4. Deploy. First boot runs `Base.metadata.create_all`, which creates the
   `users` table in Supabase. Existing tables are left alone.

Check it came up:

```bash
curl https://<your-service>.onrender.com/health
```

## 3. Seed the demo accounts

Render's free plan has no shell, so run the seed from your machine pointed at
Supabase:

```powershell
cd backend
$env:DATABASE_URL="<the same Supabase URL>"
$env:DEMO_STAFF_PASSWORD="<pick something long>"
$env:DEMO_ORG_PASSWORD="<pick something long>"
.\venv\Scripts\python.exe -m scripts.upgrade_schema   # first deploy of the intake pipeline only
.\venv\Scripts\python.exe -m scripts.seed_demo
```

Both run from `backend/`, which is where `app/` and `scripts/` live.

`upgrade_schema` adds the intake tables and columns to a database that
predates them, and backfills expiration deadlines onto existing items —
without it, older stock has no deadlines and the sweep cannot see it. It is
idempotent and a no-op once the database is current, and Render also runs it
on every deploy via `preDeployCommand`, so this manual run matters only if
you seed before the first deploy.

`seed_demo` writes to the shared team database — the two demo users, a
verified demo pantry, the default expiration rules, a small UPC catalog, and
sample shelves and items. Re-running updates rather than duplicates.

## 4. Point Vercel at the API

In the Vercel project → Settings → Environment Variables:

```
VITE_API_URL = https://<your-service>.onrender.com
```

**Then trigger a redeploy.** Vite inlines `VITE_*` variables at *build* time,
not runtime — saving the variable alone changes nothing. Deployments → ⋯ →
Redeploy.

## 5. Confirm the round trip

Open the Vercel URL and sign in as the demo staff account. If the login
button spins and fails, open DevTools → Network:

| Symptom | Cause |
|---|---|
| CORS error in console | `CORS_ORIGINS` on Render doesn't exactly match the Vercel origin |
| Request goes to `localhost:8000` | Vercel wasn't redeployed after setting `VITE_API_URL` |
| 502 / long hang on first load | Free service spinning up — see below |
| 500 on login | Check Render logs; usually `DATABASE_URL` |

---

## Known constraints

**Free services sleep.** After 15 minutes idle, Render spins the service down;
the next request takes ~50 seconds to wake it. That's a bad first impression
in a live demo — load the site a minute before you present, or upgrade to the
paid tier for anything you're being graded on.

**The expiry sweep still doesn't run.** `POST /reservations/expire-stale`
needs a caller every 5 minutes (FR-10.2). Render Cron Jobs are a paid feature;
a free GitHub Actions workflow on a schedule works just as well and can hold
the manager token as a repo secret.

**No migrations.** `create_all` creates missing tables but never alters
existing ones. The next time a column changes, it must be applied to Supabase
by hand — or Alembic adopted first (C-5).

**Build time.** `google-cloud-vision` is the largest dependency and nothing
imports it yet. If builds get slow or hit the free plan's memory ceiling,
comment it out of `requirements.txt`; re-enable when the Vision pipeline is
actually wired in.
